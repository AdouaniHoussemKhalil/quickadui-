# Theme

`@quickadui/theme` is the runtime layer over `@quickadui/tokens`' build-time
data: a `ThemeProvider` that applies the current light/dark mode (and any
accent-color override) straight to `document.documentElement`, and a
`useTheme()` hook every themeable example on this site — including its own
header — reads from. No rebuild or page reload is needed for either kind of
change.

## Mode: light / dark / system

`theme` is the user's chosen mode (`"light"`, `"dark"`, or `"system"`);
`resolvedTheme` is always `"light"` or `"dark"`, never `"system"` itself —
what this site's own header toggle is built from:

<Example
  code={`const { theme, setTheme } = useTheme();

<button onClick={() => setTheme("dark")}>{theme}</button>`}
>
  <ThemeToggle />
</Example>

## Accent color override

`colors` holds whichever families are currently overridden away from
`@quickadui/tokens`' build-time seed colors — a family absent from it is
still using its build-time color. `setColor` regenerates that family's full
12-step light+dark scale from a single `#RRGGBB` seed and applies it
immediately; `resetColor` reverts it. This site exposes exactly one family
this way — `accent` — next to the mode toggle in its own header, the same
component rendered again here:

<Example
  code={`const { colors, setColor, resetColor } = useTheme();

<input
  type="color"
  value={colors.accent ?? "#2563eb"}
  onChange={(e) => setColor("accent", e.target.value)}
/>`}
>
  <AccentPicker />
</Example>

## ThemeScript

`ThemeProvider` alone doesn't prevent a flash of the wrong theme *mode* on
first paint — pair it with `<ThemeScript />` (or `getThemeScript()` inlined
by hand) rendered as early as possible in `<head>`, ahead of
`ThemeProvider` itself, so the correct mode applies before hydration. A
stored *color* override doesn't have this treatment yet — it's applied once
`ThemeProvider` mounts, so a returning visitor with a custom accent still
sees one frame of the build-time brand color first.
